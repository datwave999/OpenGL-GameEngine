
# Current Optimizations

- **ECS:** EnTT packs components in storage pages and views select matching entities; separate pools don't automatically align by entity.
- **Assets:** Four-byte model handles share resources and use indexed lookups instead of strings during rendering.
- **Transforms:** Dirty flags skip unchanged matrix calculations, though every transform is still visited.
- **Render queue:** Reuses capacity and sorts by shader/material, but rebuilds every render and draws each command separately.
- **Lights:** Uses squared distances and partial sorting; uploads at most 16 point lights and 8 spotlights.
- **Uniforms:** Caches locations, though matrices are still uploaded per draw.

## Render Commands: Keep Matrices out of the Sort Data

- **Change:** Store three asset handles and the full `entt::entity`; fetch matrices during submission. Current command layout shrinks from 112 to 16 bytes, avoiding repeated matrix copies for model nodes.
- **Tradeoff:** Transform lookups add indirection and may reduce submission locality. Keep entities/transforms valid and unchanged between extraction and submission.
- **Measure:** Compare extraction, sorting and submission together; 85.7% less command storage doesn't imply the same frame-time reduction.

See [Graphics Pipeline](2.GraphicsPipeline.md#rendersystem-extraction---sorting---execution).

## Transforms: Track Changed Entities

- **Change:** Enqueue changed entities once and rebuild only their matrices, avoiding a full scan when few objects move.
- **Tradeoff:** Every mutation path and newly created transform must enqueue work. Duplicate prevention and validity checks add overhead; dense iteration may win when most objects move.

## Transform Data: Separate Local Data from Cached Matrices

- **Change:** Separate position/rotation/scale and dirty state from cached matrices, so gameplay and lighting traverse smaller records.
- **Tradeoff:** Keep both components consistent through creation/removal; rebuilding matrices needs access to both pools. Split fields needed by costly passes first, without requiring a full Structure of Arrays (SoA) conversion.

## Rendering: Frustum Culling

- **Change:** Test transformed model bounds against the camera frustum before creating commands, reducing sorting, uploads, draws and GPU work for offscreen objects.
- **Tradeoff:** Bounds updates and tests cost time. Bounds must conservatively include all model nodes and account for rotation/scale.

## Rendering: Instancing / Per-Instance Data

- **Change:** Batch visible objects sharing mesh/material/shader and upload transforms in an instance buffer to reduce draws and per-object uniforms.
- **Tradeoff:** Requires shader and submission changes. Each compatible model node needs its own batch; different meshes can't share an instanced draw just because their materials match.

## Rendering: Sorting / Static Draw Data

- **Change:** Test mesh as a third sort key and cache sorted node draw metadata, updating it when membership or assets change. Moving objects can use cached metadata with current transforms.
- **Tradeoff:** Shared-material edits and model changes need invalidation; culling changes visibility. Extra comparisons may outweigh saved binds, and transparent objects need separate ordering rules.

## Assets: Reduce Repeated Lookups

- **Change:** Keep frequently read node draw metadata in compact arrays and cache stable handles, refreshing them when models/materials change.
- **Tradeoff:** Preserve asset ownership/lifetime rules and avoid pointers into vectors that may grow. Reorganize only if profiling shows extraction/lookups are costly.

See [Resources](3.Resources.md).

## ECS Queries: Views / Groups

- **Change:** Benchmark views against owning groups for large populations, or gather a compact frame list that later passes reuse.
- **Tradeoff:** Groups add membership-maintenance work and ownership restrictions; frame lists cost time and duplicate data. EnTT storage pages aren't a flat array indexed by entity ID.

See [ECS Guide](4.ECS_Guide.md#views-how-systems-find-entities).

## Gameplay: Replace Repeated Named Updates

- **Change:** Cache handles for frequently accessed specific entities; use behavior components and systems when many entities share movement/rotation.
- **Benefit:** Removes repeated string lookups and groups behavior data. Named wrappers remain useful for scene setup and debugging.

See [ECS Guide](4.ECS_Guide.md#adding-a-new-behaviour--system).

## Vector Capacity / Allocation Spikes

- **Change:** Reserve render/light vector capacity from expected scene size or a recent high-water mark if profiling shows reallocation spikes.
- **Tradeoff:** Retained capacity consumes memory; reserving space doesn't guarantee CPU-cache residency.

## Lights: Remove Redundant Component Position / Direction

- **Change:** Remove cached position from `PointLightComponent` and cached position/direction from `SpotLightComponent`. Derive world values from `TransformComponent` and optional `LightOffsetComponent`, using temporary selection-cache data or computing them for selected UBO entries.
- **Benefit:** Smaller components, fewer writes and no stale derived values in gameplay data. Measure temporary storage versus recomputation.
- **Scope:** Keep position/direction in GPU structs because shaders need them. The standalone directional light's direction remains its source value.

## Lights: Reduce Candidate / Conversion Work

- **Change:** Cache unchanged derived values and converted properties within the light system; consider spatial partitioning and rejecting irrelevant lights when candidate counts grow.
- **Tradeoff:** Transform, offset and property changes need invalidation. Camera movement still requires reselection, spatial structures need maintenance, and newly selected lights need their GPU slots populated.
- **Culling:** Current radius controls attenuation; define an influence cutoff before treating it as a hard culling boundary.

## Lights: Reduce UBO Upload Work

- **Change:** Skip unchanged uploads or update changed regions if that beats uploading the full fixed-size block.
- **Tradeoff:** Tracking changes and multiple small transfers may cost more. Preserve `std140` array/count offsets, populate newly selected slots, and rewrite all needed data in invalidated regions.

See [Graphics Pipeline](2.GraphicsPipeline.md#std140-layout).

## Parallel Execution

- **Change:** Parallelize costly transform rebuilding or command extraction in batches, using per-worker output vectors and merging afterward.
- **Tradeoff:** Scheduling, synchronization, merging and cache-line contention add overhead. Coordinate registry writes/structural changes and preserve system dependencies; OpenGL submission needs the appropriate current context.

## Profiling / Choosing What to Change

- **Measure:** Time gameplay, transforms, light gathering/selection/upload, extraction, sorting and CPU submission separately. Use GPU timer queries for GPU work; CPU draw-call timings don't measure full GPU execution.
- **Stress scenes:** Test mostly static objects, moving objects, many model nodes, repeated instances, many light candidates, frequent component changes and expensive fragment workloads.
- **Compare fairly:** Use the same scene, camera path, build and VSync settings; warm up assets/capacities and record frame times plus spikes rather than only FPS.
- **Diagnose:** Hardware counters can explain stalls, cache misses and bandwidth, but judge changes by total elapsed time. Address the measured bottleneck first.
