# ECS Guide

## Basic Idea:

- ECS = Entity Component System
- **Entity**: an ID for an object (cube, car, light, etc.)
- **Component**: data attached to that entity (position, model handle, light settings)
- **System**: code that reads or changes that data (moving objects, updating lights, rendering)
- Uses `EnTT` to manage entities and their components
- an entity's components decide what the systems do with it
    - Transform + Render -> can be drawn
    - Transform + PointLight -> gives off light
    - Transform + Render + PointLight -> can be drawn AND gives off light
    - a light doesn't need a visible model to work

## The Registry:

- `entt::registry` is owned by PlayState
- stores the entities and component data
- components of the same type are stored together in their own pools [not inside the Entity wrapper]
- same-type components are packed in EnTT's storage pages; different pools don't automatically line up by entity
- systems get a reference to the registry to access this data
- AssetManager owns the models, meshes, textures, etc. Components only need handles to these assets
- when PlayState is destroyed, its registry and component data are destroyed too

## Entity Class:

`Entity` is a small wrapper around an entity ID and its registry. It can create an entity or refer to an existing one, and provides helpers to add, access, check, and remove components.

The registry owns the entity and its data. Copying a wrapper refers to the same entity; destroying the wrapper doesn't remove it. Keep wrappers within the registry's lifetime, and use `registry.valid(entity)` when an entity may have been destroyed.

## Components:

### TransformComponent:

- stores `position`, `rotation`, `scale`, `dirty`, `modelMatrix`, and `normalMatrix`.
- TransformSystem rebuilds the cached matrices when `dirty` is set. Its helpers mark changes automatically; set the flag yourself if you edit the transform directly.
- transforms are independent world transforms, with no parent/child hierarchy currently.

### RenderComponent:

- holds `modelHandle` (uint32_t): handle to a model in AssetManager
- the model contains nodes with mesh and material handles
- RenderSystem uses these handles to find what it needs to draw
- multiple entities can use the same model handle and have different transforms
- asset ownership, handles and model creation are explained in [3.Resources](3.Resources.md)

### Light Components:

- **PointLightComponent:** shines in all directions. Stores color, radius, ambient/diffuse/specular intensities, and a world position updated by LightSystem.
- **SpotLightComponent:** adds inner/outer cone angles and a world direction to the point-light settings. Its default local direction is -Z.
- **LightOffsetComponent:** optionally offsets a light's position and spotlight direction relative to its entity. Offsets rotate with the entity; scale doesn't affect the position offset.
- **DirectionalLightComponent:** stores direction and ambient/diffuse/specular colors. It is currently held by LightSystem and set through `SetDirectionalLight(...)`, rather than read from entities.

`PointLightUBOData`, `SpotLightUBOData`, and `LightUBO` are GPU upload structs. Their layout and shader usage are covered in [Graphics Pipeline](2.GraphicsPipeline.md#light-data).

## Systems:

### TransformSystem:

- **Update**:
    - gets all entities with TransformComponent
    - skips transforms where `dirty == false`
    - calculates `modelMatrix = translate * rotate * scale`
    - calculates normal matrix (inverse transpose of the model matrix's 3x3 part)
    - sets `dirty = false`
- still visits every transform each update [dirty flag skips math, not iteration]
- **Movement / Rotation Helpers**:
    - `Translate`: move along world axes
    - `MoveRelative`: move along the object's rotated local axes
    - `Rotate`: rotate around a world axis (angle in degrees)
    - `RotateRelative`: rotate around a local axis (angle in degrees)
    - Rotate pre-multiplies the rotation quaternion, RotateRelative post-multiplies it
    - both normalize the resulting quaternion; rotation axes must be non-zero
- **Setters**:
    - SetPosition, SetRotation, SetScale
    - SetRotation takes either a quaternion or pitchX, yawY, rollZ in degrees
    - quaternion setter stores the supplied value directly [keep it normalized]
    - all movement/rotation/setter helpers mark the transform dirty
- **Direction Helpers**:
    - GetForward, GetRight, GetUp: local -Z, +X, +Y rotated into world space

### LightSystem:

- **Owns**:
    - light UBO (unique_ptr), bound to base 1
    - directional light settings
    - cached vectors for sorting point lights and spotlights (reused each frame)
- **SetDirectionalLight(direction, color, diff, ambient)**:
    - stores direction and color multiplied by diffuse/ambient intensities
    - specular color uses color directly [no separate specular intensity argument]
    - use a normalized direction (current directional-light shader doesn't normalize it)
- **Update**:
    - finds entities with Transform + PointLight, then Transform + SpotLight
    - calculates their world positions and spotlight directions
    - applies LightOffsetComponent if present
    - selects closest lights using squared camera distance and partial_sort
    - uploads at most 16 point lights and 8 spotlights.
    - converts intensities, radius, and cutoff angles into shader data
    - uploads the LightUBO to GPU
- lights beyond these limits still exist in the registry, but aren't uploaded that frame
- selection uses distance to the camera.
- position = transform position + rotation * localOffset (if present)
- spotlight direction = rotation * local -Z, or rotation * normalized directionOffset (if present)
- transform scale isn't applied to light offsets or radius
- attenuation and cutoff conversions are explained in [Graphics Pipeline](2.GraphicsPipeline.md#light-data)

### RenderSystem:

- **Render**:
    - gets entities with both RenderComponent and TransformComponent
    - finds each entity's model using AssetManager
    - uses the model's nodes and cached transform matrices to submit the scene
- uses the matrices already calculated by TransformSystem.
- one entity can produce multiple draw calls if its model has multiple nodes
- command extraction, sorting and draw execution are explained in [Graphics Pipeline](2.GraphicsPipeline.md#rendersystem-extraction---sorting---execution)

## Using ECS in PlayState:

Create entities and attach their components in `PlayState::Initialize()`. For example, after creating or loading `floorModel` through AssetManager:

```cpp
Entity floor(&registry);
floor.AddComponent<TransformComponent>(glm::vec3(0.0f, -1.0f, 0.0f));
floor.AddComponent<RenderComponent>(floorModel);
entities["floor"] = floor;
```

The `entities` map is only for convenient access to named objects; the registry keeps them alive independently of their wrappers.

- **Moving objects:** get their TransformComponent in `Update()` and use TransformSystem's helpers. Multiply movement or rotation speed by `dt`; direct edits must set `dirty = true`.
- **Adding lights:** attach a TransformComponent and a PointLightComponent or SpotLightComponent. Add LightOffsetComponent when the light should come from a particular part of a model, and RenderComponent if it needs a visible mesh.
- **Removing objects:** `EraseComponent<T>()` removes a component; `registry.destroy(entity)` removes the entity and its components. Remove any named wrapper from the map too, and discard references to removed components.
- **Accessing existing objects:** use `find` or `at` for named entities. If an entity may have been removed, check `registry.valid(entity)` before accessing its components, then use `HasComponent<T>()` to check for the data you need.

## Views (How Systems Find Entities):

```cpp
auto view = registry.view<TransformComponent, RenderComponent>();

view.each([](auto entity, auto& tc, auto& rc) {
    // Runs once for each entity that has BOTH components
});
```

- view filters entities by the component types requested
- no need to store every object in a map or check every entity manually
- to add new behaviour: create a component for its data, then a system that processes a matching view
- call that system from PlayState in the order it needs to run

## System Order / Lifetime Rules:

- gameplay systems that change transforms run before TransformSystem.Update
- TransformSystem produces the cached matrices RenderSystem reads
- LightSystem reads position/rotation directly from transforms and selects lights using current camera position
- RenderSystem runs in PlayState.Render, after update work
- Camera and Input remain separate from ECS
- full frame order and pause behavior are explained in [1.Architecture](1.Architecture.md#current-frame-order)
- [IMP] keep Entity IDs/asset handles for later access; component references are temporary access to registry storage
- collect entities to remove, then destroy them after a view pass when removal would interfere with that pass
- changing components/entities doesn't unload shared assets
