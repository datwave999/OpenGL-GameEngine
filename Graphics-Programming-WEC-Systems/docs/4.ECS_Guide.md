# ECS Guide

## Basic Idea:

- ECS = Entity Component System
- **Entity**: an ID for an object (cube, car, light, etc.)
- **Component**: data attached to that entity (position, model handle, light settings)
- **System**: code that reads or changes that data (moving objects, updating lights, rendering)
- Uses `EnTT` to manage entities and their components
- an entity's components decide what the systems do with it
    - Transform + Render -> can be drawn
    - Transform + PointLight -> gives off light
    - Transform + Render + PointLight -> can be drawn AND gives off light
    - a light doesn't need a visible model to work

## The Registry:

- `entt::registry` is owned by PlayState
- stores the entities and component data
- components of the same type are stored together in their own pools [not inside the Entity wrapper]
- same-type components are packed in EnTT's storage pages; different pools don't automatically line up by entity
- systems get a reference to the registry to access this data
- AssetManager owns the models, meshes, textures, etc. Components only need handles to these assets
- when PlayState is destroyed, its registry and component data are destroyed too

## Entity Class:

- **Holds** (Private variables):
    - `m_EntityHandle`: the entity's ID
    - `m_Registry`: pointer to the registry it belongs to
- **Creating an Entity**:
    - `Entity(&registry)`: creates a new entity in the registry
    - `Entity(handle, &registry)`: wraps an existing entity ID
    - default constructor: empty wrapper [no entity created]
- **Helper Functions**:
    - `AddComponent<T>(...)`: adds a component and returns a reference to it
    - `GetComponent<T>()`: gets a reference to an existing component
    - `HasComponent<T>()`: checks if the entity has that component
    - `EraseComponent<T>()`: removes that component
- [IMP] only add a component once, and only get it if it exists
- copying an Entity copies the ID and registry pointer [both wrappers refer to the same entity]
- destroying the wrapper does not destroy the entity in the registry
- `if (entity)` only checks that the ID isn't `entt::null`. Use `registry.valid(entity)` to check if it is still alive
- conversions to entt::entity and uint32_t expose the ID [it isn't an asset handle]
- [IMP] wrappers can't outlive their registry, even if their stored ID isn't null

## Components:

### TransformComponent:

- **Variables**:
    - `position`: position in world space (default = 0)
    - `rotation`: quaternion storing orientation (default = no rotation)
    - `scale`: size along each axis (default = 1)
    - `dirty`: whether the matrices need to be calculated again (default = true)
    - `modelMatrix`: takes model coordinates into world space
    - `normalMatrix`: used to transform normals for lighting
- changing position/rotation/scale doesn't automatically update the matrices
- use TransformSystem's helpers (they set `dirty = true`), or set it manually after changing the data
- transforms are independent world transforms [no parent/child transform hierarchy currently]
- use non-zero scale values if the normal matrix needs to be invertible

### RenderComponent:

- holds `modelHandle` (uint32_t): handle to a model in AssetManager
- the model contains nodes with mesh and material handles
- RenderSystem uses these handles to find what it needs to draw
- multiple entities can use the same model handle and have different transforms
- asset ownership, handles and model creation are explained in [3.Resources](3.Resources.md)

### Light Components:

- **PointLightComponent**:
    - color, radius, diffuse/ambient/specular intensities
    - cached world position [updated by LightSystem from the transform]
    - shines in all directions
- **SpotLightComponent**:
    - same basic light settings + inner and outer cutoff angles (in degrees)
    - cached world position and direction [updated by LightSystem]
    - shines in a cone, default local direction is -Z
- **LightOffsetComponent** (optional):
    - `localOffset`: light's position relative to the entity's position
    - `directionOffset`: local direction used by spotlights
    - offsets rotate with the entity [scale is not applied to the position offset]
    - useful when the light should come from a particular part of a model
- **DirectionalLightComponent**:
    - direction and ambient/diffuse/specular colors
    - currently stored in LightSystem, set using `SetDirectionalLight(...)`
    - [IMP] attaching this component to an entity doesn't make the system use it currently
- PointLightUBOData, SpotLightUBOData and LightUBO are GPU upload structs [not components we add to entities]
- their layout and shader usage are explained in [Graphics Pipeline](2.GraphicsPipeline.md#light-data)

## Systems:

### TransformSystem:

- **Update**:
    - gets all entities with TransformComponent
    - skips transforms where `dirty == false`
    - calculates `modelMatrix = translate * rotate * scale`
    - calculates normal matrix (inverse transpose of the model matrix's 3x3 part)
    - sets `dirty = false`
- still visits every transform each update [dirty flag skips math, not iteration]
- **Movement / Rotation Helpers**:
    - `Translate`: move along world axes
    - `MoveRelative`: move along the object's rotated local axes
    - `Rotate`: rotate around a world axis (angle in degrees)
    - `RotateRelative`: rotate around a local axis (angle in degrees)
    - Rotate pre-multiplies the rotation quaternion, RotateRelative post-multiplies it
    - both normalize the resulting quaternion; rotation axes must be non-zero
- **Setters**:
    - SetPosition, SetRotation, SetScale
    - SetRotation takes either a quaternion or pitchX, yawY, rollZ in degrees
    - quaternion setter stores the supplied value directly [keep it normalized]
    - all movement/rotation/setter helpers mark the transform dirty
- **Direction Helpers**:
    - GetForward, GetRight, GetUp: local -Z, +X, +Y rotated into world space

### LightSystem:

- **Owns**:
    - light UBO (unique_ptr), bound to base 1
    - directional light settings
    - cached vectors for sorting point lights and spotlights (reused each frame)
- **SetDirectionalLight(direction, color, diff, ambient)**:
    - stores direction and color multiplied by diffuse/ambient intensities
    - specular color uses color directly [no separate specular intensity argument]
    - default light is black until this is called
    - use a normalized direction (current directional-light shader doesn't normalize it)
- **Update**:
    - finds entities with Transform + PointLight, then Transform + SpotLight
    - calculates their world positions and spotlight directions
    - applies LightOffsetComponent if present
    - selects closest lights using squared camera distance and partial_sort
    - uploads at most 16 point lights and 8 spotlights [current GPU limits]
    - converts intensities, radius, and cutoff angles into shader data
    - uploads the LightUBO to GPU
- lights beyond these limits still exist in the registry, but aren't uploaded that frame
- selection uses distance to the camera, without testing whether a light affects visible objects
- position = transform position + rotation * localOffset (if present)
- spotlight direction = rotation * local -Z, or rotation * normalized directionOffset (if present)
- transform scale isn't applied to light offsets or radius
- use a positive radius, a non-zero directionOffset and inner cutoff angle < outer cutoff angle
- attenuation and cutoff conversions are explained in [Graphics Pipeline](2.GraphicsPipeline.md#light-data)

### RenderSystem:

- **Render**:
    - gets entities with both RenderComponent and TransformComponent
    - finds each entity's model using AssetManager
    - uses the model's nodes and cached transform matrices to submit the scene
- uses the matrices already calculated by TransformSystem [doesn't calculate transforms itself]
- one entity can produce multiple draw calls if its model has multiple nodes
- invalid model handle is skipped; other referenced assets are assumed valid
- command extraction, sorting and draw execution are explained in [Graphics Pipeline](2.GraphicsPipeline.md#rendersystem-extraction---sorting---execution)

## Using ECS in PlayState:

### Create an Object:

Example inside `PlayState::Initialize()`, after `floorModel` has been created:

```cpp
Entity floor(&registry);
floor.AddComponent<TransformComponent>(glm::vec3(0.0f, -1.0f, 0.0f));
floor.AddComponent<RenderComponent>(floorModel);

// Keep a wrapper if we want to access this specific object later
entities["floor"] = floor;
```

- AddComponent forwards its arguments to construct the component
- values not supplied use the component's defaults
- the local wrapper can go out of scope; the registry still keeps the entity
- `entities` is just a map for accessing named test objects [not required for ECS to work]

### Change a Transform:

Example inside `PlayState::Update(float dt)`:

```cpp
auto& floorTc = entities.at("floor").GetComponent<TransformComponent>();
transformSystem.Rotate(floorTc, 30.0f * dt, glm::vec3(0.0f, 1.0f, 0.0f));
```

- multiply movement/rotation speed by dt so it depends on time, not frame count
- if changing fields directly:

```cpp
floorTc.position.y = -2.0f;
floorTc.dirty = true;
```

### Create a Light:

```cpp
Entity light(&registry);
light.AddComponent<TransformComponent>(glm::vec3(0.0f, 3.0f, 0.0f));
light.AddComponent<PointLightComponent>(glm::vec3(1.0f, 0.0f, 0.0f));
```

- this creates a red point light with the remaining settings at their defaults
- add RenderComponent too if we want a visible model for it
- change its TransformComponent to move the light [cached light position gets overwritten during Update]

### Create a Spotlight with an Offset:

Example inside PlayState::Initialize(), after the flashlight model has been loaded:

```cpp
Entity lamp(&registry);
lamp.AddComponent<TransformComponent>(glm::vec3(0.0f, 3.0f, 0.0f));

auto& spot = lamp.AddComponent<SpotLightComponent>();
spot.color = glm::vec3(1.0f, 1.0f, 0.0f);
spot.radius = 30.0f;
spot.innerCutOffAngle = 12.5f;
spot.outerCutOffAngle = 17.5f;

auto& offset = lamp.AddComponent<LightOffsetComponent>();
offset.localOffset = glm::vec3(0.0f, 0.0f, -0.5f);
offset.directionOffset = glm::vec3(0.0f, 0.0f, -1.0f);

lamp.AddComponent<RenderComponent>(flashLightModel);
```

- light starts half a unit in front of the entity along its local -Z axis
- rotating the entity rotates both the offset and the spotlight direction
- adding RenderComponent makes the model visible, it doesn't create the light
- position offset stays half a unit even if the model is scaled

### Remove Components / Entities:

```cpp
if (light.HasComponent<PointLightComponent>()) {
    light.EraseComponent<PointLightComponent>();
}

registry.destroy(light);
```

- removing the light component stops it giving off light, but keeps the entity
- `registry.destroy(...)` removes the entity and all its components
- remove any wrappers for that entity from the map too [they now refer to a destroyed entity]
- don't use old component references after their component/entity is removed
- removing a component can move another component in that pool; get references again after removals
- removing a named wrapper alone doesn't destroy the registry entity

### Access an Entity that Might Have Been Removed:

```cpp
auto found = entities.find("floor");
if (found != entities.end() && registry.valid(found->second)
    && found->second.HasComponent<TransformComponent>()) {
    auto& tc = found->second.GetComponent<TransformComponent>();
    transformSystem.SetPosition(tc, glm::vec3(0.0f, -2.0f, 0.0f));
}
```

- find/at access existing names; entities["name"] inserts an empty wrapper if the name is missing
- check validity before accessing components of an entity that might have been destroyed
- HasComponent only checks membership, it doesn't make a stale wrapper safe to use

## Views (How Systems Find Entities):

```cpp
auto view = registry.view<TransformComponent, RenderComponent>();

view.each([](auto entity, auto& tc, auto& rc) {
    // Runs once for each entity that has BOTH components
});
```

- view filters entities by the component types requested
- no need to store every object in a map or check every entity manually
- to add new behaviour: create a component for its data, then a system that processes a matching view
- call that system from PlayState in the order it needs to run

## Adding a New Behaviour / System:

Example: rotating objects based on a component, instead of writing one named update for each object

### Component (AngularVelocityComponent.h):

Create under include/ECS/Components:

```cpp
#pragma once
#include <glm/glm.hpp>

struct AngularVelocityComponent {
    float degreesPerSecond{ 30.0f };
    glm::vec3 worldAxis{ 0.0f, 1.0f, 0.0f };
};
```

- component only holds the rotation settings
- worldAxis must be non-zero (Rotate normalizes it)

### System (AngularVelocitySystem.h):

Create under include/ECS/Systems:

```cpp
#pragma once
#include <entt/entt.hpp>
#include "ECS/Components/AngularVelocityComponent.h"
#include "ECS/Systems/TransformSystem.h"

class AngularVelocitySystem {
public:
    void Update(entt::registry& registry, TransformSystem& transforms, float dt) {
        auto view = registry.view<TransformComponent, AngularVelocityComponent>();
        view.each([&](auto entity, auto& tc, const auto& angular) {
            transforms.Rotate(tc, angular.degreesPerSecond * dt, angular.worldAxis);
        });
    }
};
```

- only entities with BOTH components rotate
- Rotate marks the transform dirty; matrix calculation stays in TransformSystem
- no registry ownership or per-object string lookup in this system

### Connect it to PlayState:

- include AngularVelocitySystem.h in PlayState.h and add this private member:

```cpp
AngularVelocitySystem angularVelocitySystem;
```

- add the component in PlayState::Initialize(), after the flag entity already has its transform:

```cpp
auto& angular = entities.at("flag").AddComponent<AngularVelocityComponent>();
angular.degreesPerSecond = 40.0f;
angular.worldAxis = glm::vec3(0.0f, 0.0f, 1.0f);
```

- replace the flag's existing manual rotation with the system call in PlayState::Update():

```cpp
// After the pause check and other gameplay changes, before matrix calculation
angularVelocitySystem.Update(registry, transformSystem, dt);
transformSystem.Update(registry);
```

- replace the existing transformSystem.Update call with this pair [call it once]
- remove the old flag rotation, otherwise both paths rotate it
- add the new headers to the Visual Studio project so they appear with the other ECS files
- these are extension examples; AngularVelocityComponent/System aren't currently part of the engine

## System Order / Lifetime Rules:

- gameplay systems that change transforms run before TransformSystem.Update
- TransformSystem produces the cached matrices RenderSystem reads
- LightSystem reads position/rotation directly from transforms and selects lights using current camera position
- RenderSystem runs in PlayState.Render, after update work
- Camera and Input remain separate from ECS
- full frame order and pause behavior are explained in [1.Architecture](1.Architecture.md#current-frame-order)
- [IMP] keep Entity IDs/asset handles for later access; component references are temporary access to registry storage
- collect entities to remove, then destroy them after a view pass when removal would interfere with that pass
- changing components/entities doesn't unload shared assets
