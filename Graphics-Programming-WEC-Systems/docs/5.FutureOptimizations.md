# Future Optimizations

## Basic Idea:

- possible improvements as the engine/scene grows [not implemented yet]
- current scene is small, most of these changes need a larger workload to show a useful difference
- DOD = organize data around the work that reads/writes it
- keep the data needed by each pass compact, avoid moving unrelated data through that pass
- [IMP] smaller structs, fewer cache misses or fewer allocations don't automatically mean a faster frame
- measure the entire affected pipeline before keeping a change

## What is Already Optimized:

- **ECS Storage**:
    - components of the same type are packed in EnTT's storage pages
    - systems select matching components instead of checking every type of object manually
    - different component pools don't automatically line up by entity
- **Asset Handles**:
    - RenderComponent only stores a four-byte model handle
    - entities share models/meshes/materials instead of owning separate copies
    - runtime getters use vector indices [no string map lookup in the render loop]
- **Transforms**:
    - dirty flag skips matrix calculations for unchanged transforms
    - still scans every TransformComponent each update
- **Render Queue**:
    - reuses vector capacity
    - sorts by shader, then material to reduce repeated binds
    - still rebuilds commands every render and makes one draw call per command
- **Lights**:
    - compact entity + distance records for selection
    - squared distance avoids square roots during selection
    - partial_sort only orders the closest lights needed
    - uploads at most 16 point lights and 8 spotlights [limits fragment shader work, excludes extra lights]
- **Uniforms**:
    - locations are cached per shader
    - matrix uniforms are still updated for every draw
- these choices save work already, but don't remove every lookup, scan or draw call

## Render Commands: Keep Matrices out of the Sort Data

- **Currently**:
    - RenderCommand holds three asset handles + modelMatrix + normalMatrix
    - current project layout = 112 bytes (12 bytes of handles + 100 bytes of matrices)
    - a model with multiple nodes copies the same entity's matrices into every node's command
    - sorting moves these matrices even though the comparator only reads shader/material handles
- **Proposed Change**:
    - keep shaderHandle, materialHandle, meshHandle and entt::entity
    - current layout would be 16 bytes (four fields, four bytes each)
    - extract handles + entity ID, sort commands, then get TransformComponent by reference during submission
    - matrices stay in the registry until the renderer needs them
- **Main Saving**:
    - 85.7% less command storage in the current configuration
    - avoids matrix copies during extraction and reduces the amount of data moved during sorting
    - particularly useful with many commands or multi-node models
- **Tradeoff**:
    - current queue gives submission sequential access to copied matrices
    - entity lookup adds indirection; shader/material order can jump around transform storage
    - still reads and uploads the same matrices for each draw
- [IMP] 85.7% less queue storage isn't 85.7% less total bandwidth or frame time
- four 16-byte commands occupy 64 bytes, but cache-line size and queue alignment determine how they fit into cache lines
- use the full entt::entity value [contains the entity version too, not just a packed-array index]
- keep entities/transforms alive and unchanged between extraction and submission
- compare extraction + sorting + submission together, not sorting alone
- current command/draw behavior is explained in [Graphics Pipeline](2.GraphicsPipeline.md#rendersystem-extraction---sorting---execution)

## Transforms: Track Changed Entities

- **Currently**:
    - TransformSystem visits every transform, checks dirty and only recalculates changed matrices
    - saves math, but still reads widely spaced flags in large component records
- **Proposed Change**:
    - maintain a list of entities whose transforms changed
    - movement/rotation/setter helpers mark dirty AND enqueue the entity once
    - process that list, refresh matrices, then clear it
- **Useful When**:
    - many transforms exist, but only a small portion move each frame
- **Tradeoff**:
    - enqueueing, duplicate prevention and validity checks add work
    - new entities need their initial matrices calculated too
    - direct field edits must also register the change [dirty = true alone wouldn't enqueue it]
    - dense iteration can be better when most entities move
- [IMP] every transform mutation path needs to participate, otherwise rendering can use old matrices

## Transform Data: Separate Local Data from Cached Matrices

- **Currently**:
    - position, rotation, scale, dirty, modelMatrix and normalMatrix share one TransformComponent
    - light gathering only needs position/rotation, but those fields are spaced by the full component size
- **Proposed Change**:
    - separate local transform settings from calculated matrices
    - gameplay/lighting access local data, rendering accesses cached matrices
    - TransformSystem reads local data and writes the matrix data
- **Main Saving**:
    - passes that only need positions or flags traverse smaller records
    - less unrelated data competes for cache space
- **Tradeoff**:
    - another storage/query relationship to maintain
    - both pieces need to stay consistent when entities/components are created or removed
- ECS separates component types, but each component record is still an AoS element (Array of Structures)
- SoA (Structure of Arrays) separates fields into their own arrays, useful when a pass processes the same field across many objects
- [IMP] start with the fields a costly pass actually uses; a full SoA conversion isn't required for DOD

## Rendering: Frustum Culling

- **Currently**:
    - every entity with Render + Transform is submitted, even if it is outside the camera's view
- **Proposed Change**:
    - store mesh/model bounds and transform them for the entity
    - test bounds against the camera frustum before creating its draw commands
- **Main Saving**:
    - fewer commands to sort, uniforms to upload and draws to submit
    - avoids GPU work for rejected objects too
- **Useful When**:
    - a large part of the scene is outside the camera's view
- **Tradeoff**:
    - bounds storage, updates and culling tests cost time
    - bounds must include every model node and account for scale/rotation
- [IMP] keep bounds conservative so visible geometry isn't incorrectly rejected

## Rendering: Instancing / Per-Instance Data

- **Currently**:
    - sorting groups similar draws, but every command still sets matrices and calls glDrawElements
- **Proposed Change**:
    - group visible objects with the same mesh/material/shader
    - upload per-instance transforms to a GPU buffer
    - draw multiple instances in one call
- **Main Saving**:
    - fewer draw calls and per-object uniform updates
    - useful for repeated objects (many trees, cubes, lamps, etc.)
- **Tradeoff**:
    - changes vertex shader inputs, buffer uploads and draw submission
    - each node of a multi-mesh model needs its own compatible batch
    - unique meshes/materials still need separate draws
- [IMP] grouping by material alone doesn't make different meshes one instanced draw

## Rendering: Sorting / Static Draw Data

- **Currently**:
    - queue is extracted and sorted every render
    - sort key is shader + material, mesh binding only reused when consecutive commands happen to share it
- **Possible Changes**:
    - test meshHandle as a third sort key
    - cache shader/material/mesh metadata for model nodes instead of looking it up repeatedly
    - keep static draw metadata sorted and update it when membership/assets change
- cached metadata can still reference current transforms; a moving object doesn't necessarily need new mesh/material metadata
- **Tradeoff**:
    - creation/removal, model changes and shared-material edits must invalidate the affected cache
    - culling changes which commands are visible each frame
    - extra sorting comparisons may cost more than the mesh binds they save
- [IMP] transparent scene objects need their own ordering rules; shader/material sorting alone isn't sufficient

## Assets: Reduce Repeated Lookups

- **Currently**:
    - handles avoid string lookups, but extraction follows model -> nodes -> materials
    - some objects and resource wrappers live in separate allocations
- **Proposed Change**:
    - put frequently read draw metadata in compact arrays
    - cache stable node handles and refresh them when models/materials change
    - keep asset ownership separate from the metadata used by the render pass
- **Useful When**:
    - profiles show asset lookup/extraction taking a substantial part of CPU time
- [IMP] don't retain pointers into asset-struct vectors across growth; handles can be used to fetch current data
- don't reorganize resource ownership just because allocations are separate [measure whether those lookups matter]
- asset lifetime and shared-material edits are explained in [3.Resources](3.Resources.md)

## ECS Queries: Views / Groups

- **Currently**:
    - render/light systems use multi-component views
    - views check membership and fetch matching data from separate component pools
- **Proposed Change**:
    - benchmark views against owning groups for large, frequently processed populations
    - groups can arrange owned component pools for joint iteration
    - alternatively, build a compact frame list once if later passes can reuse it
- **Tradeoff**:
    - groups add work when component membership changes
    - group ownership rules restrict which components can be rearranged together
    - gathering a frame list costs time and can duplicate data
- [IMP] components are packed within pages, not one guaranteed flat array indexed by entity ID
- current view/component behavior is explained in [ECS Guide](4.ECS_Guide.md#views-how-systems-find-entities)

## Gameplay: Replace Repeated Named Updates

- **Currently**:
    - PlayState looks up named test entities and changes each transform individually
- **Proposed Change**:
    - keep entity handles for a few specific objects accessed often
    - add behavior components + systems when many entities share the same movement/rotation
    - systems find matching entities through views
- removes repeated string lookup and keeps behavior data together
- named wrappers can remain useful for scene setup/debugging [the map doesn't defeat ECS]
- an example behavior system is explained in [ECS Guide](4.ECS_Guide.md#adding-a-new-behaviour--system)

## Vector Capacity / Allocation Spikes

- **Currently**:
    - render/light vectors are cleared and reused
    - capacity is retained, but a larger workload can still trigger reallocation
- **Proposed Change**:
    - reserve capacity using an expected scene size or recent high-water mark
    - watch extraction/light gathering for allocation spikes
- **Tradeoff**:
    - excess retained capacity consumes memory
    - reserve doesn't guarantee the data stays in CPU cache
- [IMP] only reserve enough to solve a measured allocation problem; scene sizes can change

## Lights: Reduce Candidate / Conversion Work

- **Currently**:
    - LightSystem visits every candidate, updates positions/directions and selects the closest lights each update
    - radius isn't used to reject lights that can't affect visible objects
- **Possible Changes**:
    - cache unchanged world positions/directions and converted light properties
    - use spatial partitioning when candidate counts become large
    - reject lights that can't affect the visible scene before nearest-light selection
- **Tradeoff**:
    - changes to transforms, offsets, light settings and camera all affect different parts of this work
    - stationary lights may still need reselection when the camera moves
    - spatial structures need maintenance when lights move
    - skipping conversion must still account for a different light entering a GPU array slot
- [IMP] current radius controls attenuation, not a hard influence boundary; any culling radius needs a defined cutoff

## Lights: Reduce UBO Upload Work

- **Currently**:
    - full fixed-size LightUBO is uploaded every update, even if nothing changed
- **Possible Changes**:
    - skip upload if the GPU block's contents and selected lights are unchanged
    - update only changed regions if smaller transfers actually improve frame time
- **Tradeoff**:
    - tracking changes and issuing several small updates can cost more than one full upload
    - fixed point/spot arrays and trailing active counts keep their existing offsets
    - newly selected lights must replace the data in their assigned slots
- [IMP] can't just shorten the block to the active-light count; the shader still reads the existing std140 layout
- invalidated buffer regions must have all data the shader needs rewritten
- CPU/GPU block layout is explained in [Graphics Pipeline](2.GraphicsPipeline.md#std140-layout)

## Parallel Execution

- **Currently**:
    - gameplay, transforms, camera, light updates and rendering run sequentially
- **Possible Changes**:
    - parallelize expensive transform rebuilding or command extraction when workloads justify it
    - partition work into batches, keep output vectors per worker and merge afterward
- **Tradeoff**:
    - scheduling, synchronization and merging add overhead
    - component/registry writes need coordination; structural changes can't race with readers
    - adjacent worker writes can compete for the same cache line
    - don't let several workers append to the same growing vector without coordination
- [IMP] CPU work can be distributed, but openGL submission needs the appropriate current context
- preserve system dependencies [transforms must be ready before their matrices are consumed]

## Profiling / Choosing What to Change

- **Measure Separately**:
    - gameplay updates
    - transform calculations
    - light gathering/selection/upload
    - render extraction
    - command sorting
    - CPU submission (uniforms, binds and draw calls)
    - GPU rendering time
- glDrawElements CPU time measures submission/possible stalls, not the entire GPU draw duration
- use GPU timer queries for GPU work, and CPU timings for CPU phases
- window-title FPS is a coarse counter; use actual elapsed timings when comparing changes
- **Useful Stress Scenes**:
    - many mostly static objects -> dirty tracking, layout and culling
    - many moving objects -> transform math and component bandwidth
    - many model nodes -> queue size, extraction and sorting
    - many identical mesh/material instances -> instancing
    - many light candidates -> candidate gathering and selection
    - frequent component additions/removals -> group maintenance and storage changes
    - high resolution / expensive materials -> GPU fragment work
- compare the same scene, camera path, build configuration and VSync setting
- run several frames after assets are loaded and capacities have warmed up
- record frame times and spikes, not just average FPS
- **Hardware Profiling**:
    - cache misses, memory stalls, branch mispredictions, bandwidth and instructions can explain a bottleneck
    - inspect them alongside elapsed time
    - fewer misses can still lose if the change adds enough work elsewhere
- [IMP] these are candidate improvements, not a fixed implementation order; choose based on the workload that is actually slow
